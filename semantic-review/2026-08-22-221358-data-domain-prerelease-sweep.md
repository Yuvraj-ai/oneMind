# Data and domain layer pre-release correctness sweep

A full-file review of `data/**`, `domain/model/**`, `domain/repository/**`, and `di/**` at `0f2f22b` (clean working tree, so this is not a diff review). The Room schema, the four migrations, and the FK/CASCADE topology are in good shape and well tested — the real problems are at the seams between the database, the file system, and the in-memory state the pipeline depends on. Six issues would cause user-visible wrong behaviour or silent loss of function on a shipped build; the worst are unrecoverable without clearing app data.

**Watch for:** deleting a Memory leaves its full-text index row behind, so search keeps returning rows for content that no longer exists (confirmed). A Memory whose pipeline run throws gets stuck in `PROCESSING` forever with no path out — retry refuses it and `markFailed` is unreachable (confirmed). The cloud provider is persisted but never restored after process death, so background enrichment silently runs with no AI at all (confirmed), and the one function that would restore it hangs forever (confirmed). The feed throws `too many SQL variables` past ~999 Memories on API 30 (confirmed in code, device-dependent).

**Verdict**: NEEDS_CHANGES

## High-level view

The delete path is incomplete in two directions. `MemoryRepositoryImpl.deleteMemory` relies entirely on `ON DELETE CASCADE`, which correctly clears all ten relational child tables but cannot reach `memory_search_index` — SQLite does not support foreign keys on virtual tables. The same repository's contract also explicitly delegates image-file cleanup to callers, and only one of the three callers does it.

The processing state machine is sound as a definition but is not enforced where it matters. `transitionState` reads, validates, then writes in three separate statements with no transaction, so the check that is supposed to make claiming a Memory safe does not. Worse, the worker/pipeline pair has no route out of `PROCESSING`: the first attempt sets that state, every subsequent attempt is rejected as ineligible and therefore returns success, so the retry never retries and the code that would mark it `FAILED` never runs.

Derived data is cleared only when a Memory enters the pipeline in `EDITED`. Any edit to a Memory in `SAVED`, `PROCESSING`, or `FAILED` leaves the old inferences and the old search-index document in place, and a `FAILED` Memory is never re-enqueued at all — so text the user deleted stays findable. On the retry path, re-running stages appends rather than replaces, because five of the derived tables key on an autogenerated id that the domain objects always leave at zero.

The AI provider is held in memory only. `OnboardingPreferences` persists the cloud credentials specifically so they can be restored, but nothing restores them, and the only reader collects an infinite DataStore flow so it would never return. Since `ProcessingWorker` typically runs in a freshly-started process, summarization, categorization, metadata extraction, and vision are effectively never available in the background.

Two queries scale with the whole corpus rather than a page: the feed passes every Memory id into `IN (:ids)`, which exceeds SQLite's 999-parameter limit on API 30.

Migrations are the strongest part of this layer. All three are additive, hand-written rather than destructive, the v4 backfill is a deliberate SQL mirror of `SearchDocument.build`, and the tests cover each hop, the skip paths, and a Room-open validation after each. Foreign-key indices are complete on every child column.

<summary>Issues (16)</summary>

1. **Search index survives Memory deletion** — `deleteMemory` only deletes DB rows; `memory_search_index` is an FTS4 virtual table and cannot cascade. Delete the index row explicitly, in the same transaction as the Memory delete.
2. **Memory stuck permanently in PROCESSING** — after a throwing first attempt, every WorkManager retry is rejected as ineligible and returns success, so `markFailed` never runs and no state ever moves. Make the worker reclaim its own `PROCESSING` Memory on retry, or sweep stale `PROCESSING` rows on startup.
3. **Cloud provider never restored after process death** — `ProviderManager` state is in-memory and only Settings/Onboarding set it, so background pipeline runs have no provider. Restore from `OnboardingPreferences` before the pipeline runs.
4. **`getCloudConfig()` never returns** — it collects `DataStore.data`, which never completes. Use `.first()`. Currently uncalled, so this is a trap for the fix to #3.
5. **`IN (:ids)` exceeds SQLite's parameter limit** — the feed passes all Memory ids to `getSummaries` and `getCategoriesForMemories`; API 30 caps bound variables at 999. Chunk the id lists.
6. **Retry duplicates derived data** — `ocr_results`, `vision_results`, `extracted_urls`, `extracted_dates`, `extracted_entities` key on an autogenerated id that domain objects leave at 0, so `OnConflictStrategy.REPLACE` never fires and a `FAILED` retry appends a second copy of everything. Delete-then-insert per Memory, or clear derived data on the retry path too.
7. **Editing a non-READY Memory leaves deleted text searchable** — clearing is gated on entry state `EDITED`, which only the `READY` edit path produces; a `FAILED` Memory is additionally never re-enqueued. Transition on any edit, and make `FAILED` and `PROCESSING` edits eligible.
8. **`transitionState` is not atomic** — read, validate, write as three statements lets two callers both pass the guard. Wrap in `@Transaction` or make it a conditional `UPDATE ... WHERE processingState = :expected`.
9. **`clearDerivedData` is not atomic** — only the first of its four calls is transactional, despite the DAO comment claiming a crash cannot leave half-stale enrichments. Wrap all four.
10. **Removed image attachments orphan their files** — `ComposerViewModel.onImageRemoved` drops the attachment from state and never deletes the canonical or thumbnail file already written to internal storage.
11. **Capture failures orphan image files** — both capture paths write the image before `createMemory`; if the insert throws, the files stay on disk with nothing referencing them.
12. **Bitmap recycled while ML Kit may still use it** — `MlKitTextRecognizer` recycles in `finally` with no `invokeOnCancellation`, so cancelling a run (which happens on Memory delete) recycles a bitmap the native recognizer still holds.
13. **Full-resolution decode without subsampling** — `ImageFileStorage.saveImage(sourceFilePath)` calls `BitmapFactory.decodeFile` with no `inSampleSize` before downscaling; a 12MP import allocates ~48MB. Decode bounds first and subsample.
14. **`CancellationException` swallowed in two places** — `ProcessingWorker.doWork` and `ModelDownloadManager.downloadModel` both `catch (Exception)`; in the download flow the subsequent `emit` from a catch block violates flow exception transparency. Rethrow cancellation.
15. **`renameTo` result ignored** — `ModelDownloadManager` emits `Completed` with a path that has no file if the rename fails.
16. **`insertMemory` uses REPLACE against a cascading FK** — a `createMemory` call carrying a non-zero id would delete the existing row and cascade away all its content blocks and derived data. Latent (all current callers pass id 0); REPLACE buys nothing here.

### Delete leaves the search index behind

`MemoryRepositoryImpl.deleteMemory` (lines 136-139) is a single DAO call, justified by a comment that derived rows cascade from the `memories` foreign key. That is true for all ten relational child tables. It is not true for `memory_search_index`: SQLite does not support foreign keys on virtual tables, so the FTS4 index has no FK and no cascade.

The index's need for explicit maintenance was understood elsewhere — `DerivedDataRepositoryImpl.clearDerivedData` (line 89) calls `searchIndexDao.delete(memoryId)` with a comment explaining exactly why. The delete path never got the same treatment. `SearchIndexDao.delete` already exists and is already wired through `SearchIndexRepository.remove`; nothing calls it from the delete path.

```
memories ──CASCADE──> content_blocks, ocr_results, vision_results,
                      extracted_urls, extracted_dates, extracted_entities,
                      memory_summaries, memory_embeddings,
                      memory_categories, memory_categorization

memories ─── ✗ ─────> memory_search_index   (FTS4 virtual table, no FK possible)
```

The downstream effect is a wrong result set rather than a crash. `SearchIndexDao.match` applies `LIMIT :limit` in SQL, `KeywordSearcher` over-fetches 3x and then scores, and `SearchOrchestrator` hydrates candidates via `getMemoriesByIds` — which silently omits ids that no longer exist. Stale rows consume slots inside the SQL `LIMIT` window and can push real matches out of it, and the resulting list is shorter than the user asked for with no indication why. `indexedCount()` also becomes a lie. Confirmed.

### No route out of PROCESSING

`ProcessingWorker.doWork` (lines 29-45) treats every pipeline outcome as success and only retries on an escaping exception. `ProcessingPipeline.run` (lines 38-42) rejects any Memory whose entry state is not `SAVED`, `EDITED`, or `FAILED`.

Trace a throwing first attempt:

1. Attempt 1: entry state `SAVED` → transitions to `PROCESSING` → something throws → `runAttemptCount` is 0, so `Result.retry()`.
2. Attempt 2: entry state is now `PROCESSING` → `NotEligible` returned, no exception → `Result.success()`.

Work is complete, the Memory is `PROCESSING`, and `markFailed` — the only thing that would move it to `FAILED` — is never reached, because it only runs from the exception branch on the final attempt. `retryProcessing` in the feed requires `FAILED`, and `PROCESSING` has no self-transition, so the user has no way to recover. Process death mid-run produces the same terminal state with no queued work at all, and nothing sweeps stale `PROCESSING` rows on startup (grep for `ProcessingState.PROCESSING` across `main` returns only the pipeline itself and the spinner in `MemoryCard`). The Memory also never reaches `SearchIndexStage`, so it is not findable. Confirmed.

An `OutOfMemoryError` or any other `Error` in a stage lands in the same place: the per-stage `catch (e: Exception)` and the worker's `catch (_: Exception)` both miss it.

### The provider is configured in one process and needed in another

`ProviderManager` (lines 21-25) keeps the active provider in `MutableStateFlow`s with no persistence and no initialisation from storage. The only writers are `SettingsViewModel` and `OnboardingViewModel`. `OnboardingPreferences` does persist everything needed (`cloud_base_url`, `cloud_api_key`, `cloud_model_name`, `cloud_supports_vision`), and `OneMindApplication.onCreate` reads none of it.

`ProcessingWorker` runs under WorkManager, which routinely starts the app process solely to execute the worker. In that process no ViewModel has run, so `getProvider()` is null, `ProviderTextGenerator.isAvailable()` and `ProviderImageDescriber.isAvailable()` are false, and the summarization, categorization, metadata-extraction, and vision stages all report unavailable. Since `ModelRegistry.generativeModels` is deliberately empty (ADR-0002), cloud is the only real provider — so this is not a degraded path, it is the whole generative feature set silently off for essentially every background run. Confirmed.

The function that would fix it is itself broken. `OnboardingPreferences.getCloudConfig()` (lines 70-83):

```kotlin
suspend fun getCloudConfig(): CloudConfig? {
    var config: CloudConfig? = null
    context.dataStore.data.collect { prefs -> ... }   // never completes
    return config
}
```

`DataStore.data` is an infinite flow. `collect` suspends forever and the `return` is unreachable. It has no callers today, and it is precisely the function a fix for the restore gap would reach for. Confirmed.

### Unbounded IN clauses

`MemoryRepositoryImpl.observeAllMemories` (lines 44-47) builds `ids` from every row the feed query returned, then passes the whole list to `derivedDataDao.getSummaries(ids)` and `categoryDao.getCategoriesForMemories(ids)`. Room expands `IN (:ids)` into one bound parameter per element and does not chunk. `SQLITE_MAX_VARIABLE_NUMBER` is 999 in SQLite before 3.32, and API 30 ships 3.28 — so on Android 11 a user with 1000 Memories gets `SQLiteException: too many SQL variables` instead of a feed. `minSdk = 30`, so this ships. API 31+ raises the cap to 32766 and is unaffected. Confirmed.

`getMemoriesByIds` has the same shape but is bounded in practice by the search candidate limit.

### Retry appends instead of replacing

Five derived tables use `@PrimaryKey(autoGenerate = true) val id: Long = 0`, and their domain counterparts in `DerivedData.kt` also default `id = 0`. `DerivedMapper` copies that zero straight through, and `OcrStage` constructs `OcrResult` without an id at all. With an autogenerated key bound as null, `OnConflictStrategy.REPLACE` has nothing to conflict on — every insert is a new row.

`ProcessingPipelineTest` line 198 encodes the opposite assumption:

```
// A retry resumes rather than restarting: stages that already succeeded
// wrote real data, and re-running them will simply overwrite it.
```

That holds only for `memory_summaries`, `memory_embeddings`, and `memory_categorization`, whose primary key is `memoryId`. For OCR text, image descriptions, URLs, dates, and entities, a `FAILED` retry produces a second full set. The consequences compound: `DerivedData.derivedText()` feeds duplicated OCR into summarization and embedding through `BoundedAnalysisInput`, where the truncation budget is now spent on duplicates; `SearchDocument.build` concatenates each OCR result separately, so the indexed document contains the same text twice and term frequency is skewed; and the detail view shows duplicate entities and links. Confirmed.

### Clearing is gated on a state the edit path often does not reach

`ProcessingPipeline.run` (lines 47-51) clears derived data only when `entryState == EDITED`. The only producer of `EDITED` is `ComposerViewModel.saveMemory`, which transitions only when the existing state is exactly `READY`.

For a Memory in `FAILED`, an edit replaces the content blocks, leaves state `FAILED`, fails `onLeaveComposer`'s `eligible == SAVED || EDITED` check, and is never enqueued. The stale derived data and the stale `memory_search_index` document — describing text the user just deleted — persist indefinitely, and a query for the removed text still returns the Memory. For a Memory in `PROCESSING`, an edit swaps the blocks mid-run while earlier stages have already written inferences about the old content, with no clearing. Confirmed.

There is a related integrity gap independent of state: on every edit, `ComposerViewModel` rebuilds all `ContentBlock`s with the default `id = 0`, so `updateMemoryWithBlocks` deletes the old rows and inserts new ones with fresh rowids. `ocr_results.contentBlockId` and `vision_results.contentBlockId` are indexed but not constrained by a foreign key, so those rows now point at block ids that no longer exist. Whenever clearing does not run, they are unreachable garbage attributed to the wrong image.

### transitionState is a read-check-write race

`MemoryRepositoryImpl.transitionState` (lines 143-158) loads the Memory, calls `ProcessingState.isValidTransition`, then issues `updateProcessingState` — three statements, no transaction. The entire purpose of the guard is to let the pipeline claim a Memory exactly once (`ProcessingPipelineTest` asserts "a memory already PROCESSING is not picked up twice"), and it cannot do that when two callers can both read `SAVED` before either writes. A double claim runs the stage chain twice concurrently, which given the append behaviour above produces duplicate derived rows. Likely — the single serial WorkManager chain makes two concurrent pipeline runs hard to provoke, but the composer's transitions run outside that chain.

### clearAllDerivedData claims atomicity it does not have

`DerivedDataDao.clearAllDerivedData` is annotated `@Transaction` and documents that a crash mid-clear cannot leave half-stale enrichments. The actual clear operation is `DerivedDataRepositoryImpl.clearDerivedData` (lines 82-91), which makes four sequential calls: the transactional DAO method, then `deleteAssignments`, `deleteCategorization`, and `searchIndexDao.delete`. Only the first is atomic. A crash after it leaves the pre-edit category assignments and the pre-edit search document in place — exactly the state the comment promises is impossible. Confirmed.

### Image files outlive the rows that reference them

`MemoryRepository.deleteMemory`'s KDoc makes file cleanup the caller's job. `FeedViewModel.confirmDelete` does it correctly, collecting both `block.content` and `block.thumbnailPath` before deleting the row. The other paths do not:

- `ComposerViewModel.onImageRemoved` (line 101) removes the attachment from UI state and schedules an auto-save. The canonical and thumbnail WebP files were already written to internal storage by a previous `saveMemory`, and nothing deletes them. Every removed attachment permanently leaks two files. Confirmed.
- `ScreenCaptureService.persist` and `ShareReceiverActivity` both call `imageFileStorage.saveImage(...)` before `createMemory`. If the insert throws, the catch notifies the user and the files stay on disk unreferenced. Confirmed.

`ImageFileStorage.deleteImage(canonicalPath)` — the one method that handles the canonical/thumbnail pair correctly — has no callers.

### Bitmap lifetime across cancellation

`MlKitTextRecognizer.recognize` decodes a bitmap, wraps it in an `InputImage`, awaits ML Kit via `suspendCancellableCoroutine`, and recycles the bitmap in `finally`. The continuation has no `invokeOnCancellation`, so cancelling the coroutine does not cancel the ML Kit `Task` — but `finally` runs immediately and recycles the bitmap the native recognizer is still reading. `ProcessingScheduler.cancel` is called on every Memory delete, making this a reachable path to a native crash on a recycled bitmap. Likely.

### Decode before downscale

`ImageFileStorage.saveImage(sourceFilePath)` (lines 51-53) calls `BitmapFactory.decodeFile` at full resolution and only then resizes to `MAX_RESOLUTION`. For a screenshot that is cheap; for a photo imported through the picker it is not — a 12MP image is roughly 48MB as `ARGB_8888`, allocated in full before anything is capped. There is no `inJustDecodeBounds` pass and no `inSampleSize`. The `Bitmap` overload is unaffected: its caller already holds a decoded frame. Likely.

### Cancellation swallowed as a generic exception

Two places catch `Exception`, which in Kotlin includes `CancellationException`.

`ProcessingWorker.doWork`'s `catch (_: Exception)` then performs suspend DB writes via `markFailed` on a cancelled coroutine.

`ModelDownloadManager.downloadModel` is worse, because it emits from the catch block:

```kotlin
} catch (e: Exception) {
    emit(DownloadProgress.Failed(modelId, e.message ?: "Download failed"))
}
```

If the collector cancels — the user navigating away from the download screen — the read loop throws `CancellationException`, it is caught, and the `emit` on a cancelled flow raises `IllegalStateException: Flow exception transparency is violated`. Confirmed. The same block also ignores `tempFile.renameTo(targetFile)`'s return value, so a failed rename still emits `Completed` with a path where no file exists; `getModelPath` then returns null and the embedder fails with "model has not been downloaded".

### REPLACE against a cascading foreign key

`MemoryDao.insertMemory` uses `OnConflictStrategy.REPLACE`, and `MemoryRepositoryImpl.createMemory` passes `memory.toEntity()`, which carries `memory.id` verbatim. All three current callers construct a fresh `Memory` with the default id of 0, so this is latent. But SQLite implements REPLACE as delete-then-insert, and every child table cascades from `memories(id)` — so a single `createMemory` call with a populated id would silently destroy that Memory's content blocks and all its derived data. Confirmed as a hazard, not currently triggered.

### Categories with nothing to report

- **Foreign-key indices**: complete. Every `@ForeignKey` child column is either explicitly indexed or is an `INTEGER PRIMARY KEY` rowid alias (`memory_summaries`, `memory_embeddings`, `memory_categorization`). Room's exported `4.json` and the hand-written migration SQL agree on every table, index, uniqueness flag, and FK action.
- **Migrations**: correct. All three are additive, so no Memory content is ever rewritten; `MIGRATION_2_3` seeds through the same `CategorySeeder` the `onCreate` callback uses, with `INSERT OR IGNORE` making it idempotent against a partially-seeded database; `MIGRATION_3_4`'s backfill mirrors `SearchDocument.build` section-for-section (sortKey 1-7 against userText/summary/OCR/vision/entities/URLs/categories). `MigrationTest` covers each hop, the 1→3 and 1→4 skip paths, seeding idempotency, and a Room-open validation after each migration.
- **CASCADE/RESTRICT**: correct as written. `memory_categories.categoryId` uses RESTRICT so the vocabulary cannot be pulled out from under assignments, and `CategoryDao` deliberately exposes no category insert or delete.
- **Cursor leaks**: none. Every query goes through Room, which owns cursor lifetime; there is no raw `SupportSQLiteDatabase.query` in production code.
- **Main-dispatcher blocking**: none found. Room suspend DAOs dispatch to their own executor, `ImageFileStorage` and `ModelDownloadManager` are on `Dispatchers.IO`, `CloudModelProvider`'s HTTP call is wrapped in `withContext(Dispatchers.IO)`, and `MediaPipeEmbeddingGenerator` serialises its non-thread-safe native embedder behind a `Mutex`.
- **Scope leaks**: none in the reviewed directories. `ScreenCaptureService.serviceScope` is cancelled in `onDestroy`.
- **Type converters and vector codec**: correct. `VectorCodec` pins little-endian explicitly and validates blob length; `VectorSearcher` filters stored vectors by both `modelId` and dimension before scoring.

### Adjacent, outside the scoped directories

Flagged because they are data-loss risks and the brief asked for those, not as part of the scoped review:

- `ComposerViewModel` runs both the debounced auto-save and the final `onLeaveComposer` save in `viewModelScope`. If the activity finishes before the 3-second debounce elapses or before the final save completes, the scope is cancelled and typed text is lost.
- `ShareReceiverActivity` performs its save in `lifecycleScope`, cancelled when the activity finishes — the same shape of risk on the share path.
- `OnboardingPreferences` stores the cloud API key unencrypted in a Preferences DataStore.
- `LocalModelProvider.load()` sets `_isLoaded = true` without checking the model file exists, and `capabilities()` reports `TEXT_GENERATION`, so `isAvailable()` returns true for a provider whose `generateText` always fails with `NotImplementedError`. Stages record FAILED where NOT_SUPPORTED is the truth. Low impact only because `ModelRegistry.generativeModels` is empty by design.
